# Автокоррекция после выхода: где хранить ключи Ozon

Это проект второго этапа, а не описание уже включённого хранения. Сейчас ключи
не сохраняются на диск и удаляются по окончании сеанса. Настройка расписания
сама по себе это правило не отменяет.

## Главное различие

«Не хранить ключ на сервере» может означать три разных требования:

1. Не записывать его в файлы, БД, резервные копии и журналы веб-сервера.
   Кратковременное использование ключа в оперативной памяти разрешено.
2. Веб-сервер вообще не должен получать ключ, даже в оперативную память.
   Запросы в Ozon выполняет отдельный исполнитель.
3. Ключ не должен находиться ни на одной VM этого физического сервера.
   Тогда хранилище/исполнитель нужны на другом компьютере или у внешнего провайдера.

Новая VM на том же физическом хосте выполняет второе требование, но не третье.
Администратор гипервизора обычно имеет доступ к дискам и памяти всех его VM.

Для запроса Seller API исполнитель должен передать действующий ключ Ozon.
Кто-то должен иметь сам ключ или право выполнить запрос с его использованием.
Автономность без браузера возможна; автономность вообще без доверенного процесса,
имеющего доступ к учётным данным, — нет.

Ключ нельзя заменить хешем, как пароль входа. Argon2id позволяет проверить пароль,
но не восстановить его; Ozon нужен исходный API-ключ, а не его хеш.

## Сравнение вариантов

| Вариант | Где хранится ключ | Получает ли его веб-VM | После выхода из сайта | Основное ограничение |
|---|---|---|---|---|
| Внешний менеджер секретов → наш backend | У внешнего провайдера, зашифрованно | Да, в RAM при работе | Да | Взломанный backend может воспользоваться правом чтения секрета |
| Собственный Vault на отдельной VM → backend | На VM хранилища, зашифрованно | Да, в RAM | Да | Нужно администрировать и защищать Vault; тот же физический хост остаётся общей границей доверия |
| Внешний исполнитель запросов | В его хранилище, вне веб-VM | Нет | Да | Нужно защищать команды исполнителю и независимо ограничивать изменения цен |
| Агент на вашем компьютере | На компьютере, например через защищённое хранилище ОС | Нет, если агент сам обращается в Ozon | Да | Компьютер и агент должны работать, иметь интернет и не спать |
| Отдельный ключевой сеанс только в RAM | Только RAM исполняющего процесса | Да, если процесс на веб-VM | Да, пока жив процесс | Перезапуск/сбой уничтожает ключ, нужен повторный ввод |

## 1. Внешний менеджер секретов

Примеры: AWS Secrets Manager, Google Secret Manager, Azure Key Vault,
управляемый Vault. Ключи кабинетов хранятся отдельно, в зашифрованном виде.
Веб-приложение сохраняет только идентификатор секрета, например `ozon/fitness/api-key`.
Это имя, а не сам ключ.

Последовательность:

1. Администратор помещает ключ в менеджер секретов.
2. Планировщик запускает задачу независимо от входа пользователя на сайт.
3. Исполнитель подтверждает свою машинную идентичность и запрашивает нужный секрет.
4. Получает ключ в RAM, читает индекс, выполняет разрешённую коррекцию в Ozon.
5. Освобождает клиент и ссылки на ключ; в журнал пишет только результат без секрета.

Выход пользователя из сайта завершает его право управлять интерфейсом,
но не отменяет отдельно разрешённую фоновую задачу.

**Что даёт:** централизованное управление доступом, журнал чтения секретов,
версии и отзыв доступа; ключи не попадают в резервную копию веб-проекта.
Ротацию ключа Ozon нужно отдельно согласовать с тем, как он выпускается/отзывается
на стороне Ozon: сам менеджер секретов не обновит произвольный API-ключ автоматически.

**Чего не даёт:** защиты от активного взлома backend, которому разрешено читать
секрет. Злоумышленник может использовать то же разрешение. Поэтому права должны
быть ограничены конкретными секретами и только чтением, с отдельной учётной записью
исполнителя и журналом доступа.

На вашем сервере нет автоматически предоставленной облачной роли виртуальной
машины AWS/GCP/Azure. Нужен способ машинной аутентификации: поддерживаемая федерация,
короткоживущий токен или клиентский сертификат. Если вместо ключа Ozon просто
положить в `.env` бессрочный токен, открывающий все секреты, основной риск сохранится.

## 2. Собственный Vault на отдельной VM

Схема похожа на предыдущую, но сервер хранилища обслуживаем сами. Для изоляции
нужна отдельная VM; существующую VM PostgreSQL лучше не нагружать новой ролью.

Понадобятся: TLS, права доступа, резервное копирование зашифрованных данных,
процедура разблокировки после сбоя/перезапуска, обновления и аудит. AppRole,
агент или mTLS решают выдачу доступа, но у каждого есть исходное средство доверия:
SecretID, сертификат, машинный ключ или другой удостоверяющий механизм.

**Плюс:** контроль над инфраструктурой и доступом в своей сети.
**Минус:** хранилище становится отдельным важным сервисом. Потеря его доступа
останавливает коррекцию; приложение должно ставить задачу на паузу и уведомлять,
а не переходить к небезопасному локальному запасному ключу.

Если Vault стоит на том же физическом сервере, это разделение VM, а не вынос
секрета за пределы физического хоста. Если backend читает ключ из Vault, во время
запроса ключ всё равно есть в RAM backend.

## 3. Отдельный исполнитель: веб-сервер вообще не видит ключ

Это наиболее подходящий вариант, если важно исключить ключ именно из веб-VM.

```text
Браузер → Great Equalizer на yfweb → очередь задач → внешний исполнитель → Ozon
                                                   ↑
                                         менеджер секретов
```

Сайт хранит настройки: кабинет, кампанию, SKU, ожидаемую WB-ссылку, ограничения,
интервал и состояние задачи. Исполнитель получает ключ вне веб-сервера и сам
выполняет запросы Seller API. Веб-серверу возвращается результат без ключа.

Для строгого исключения ключа из веб-VM первоначальный ввод тоже должен идти
напрямую в отдельный доверенный сервис или через административную консоль
исполнителя. Если вводить ключ в текущую форму и пересылать через backend,
он уже побывает в памяти веб-сервера.

**Критически важно:** исполнитель не должен принимать произвольный URL,
метод API и тело запроса от сайта. Иначе взломанный сайт сможет управлять ценами
через исполнителя, даже не узнав ключ.

У исполнителя должны быть собственные проверки:

* Разрешённые кабинеты и кампании, права ключа с минимально необходимым доступом.
* Подтверждение состава и WB-ссылок по свежим данным Ozon.
* Коэффициент 0,94–1,00, автоматический шаг максимум 0,01.
* Сохранение нижних ограничений цен, без их автоматического снижения.
* Интервал запусков, блокировка параллельных задач и защита от повторной записи.
* Устойчивая запись намерения до запроса, разбор неоднозначного ответа без слепого повтора.
* Аудит изменений без ключей; явное отключение автоматики и отзыв доступа.

Взаимодействие сайта и исполнителя защищается отдельной машинной идентичностью,
например mTLS или короткоживущими токенами. Её компрометация тоже опасна, но она
может давать только ограниченные команды, а не возможность забрать ключ Ozon.

Планировщик и журнал задач лучше держать на стороне исполнителя. Тогда выход
из сайта и перезапуск веб-интерфейса не мешают уже разрешённому расписанию.
Для независимости от отказа всего вашего физического сервера исполнитель
нужно разместить на другом компьютере/хосте или у внешнего провайдера.

## 4. Агент на вашем компьютере

Агент — небольшая программа, которая запускается отдельно от браузера.
Она сама читает задания и обращается в Ozon. Для Windows возможен защищённый
контейнер учётных данных/DPAPI с отдельной учётной записью и файловыми правами.
Ключ не следует сохранять открытым текстом в `.py`, `.json` или `.env`.

Предпочтительная сеть — исходящие HTTPS-запросы агента за заданиями: открывать
доступ из интернета к вашему компьютеру не требуется. Сайт получает только результаты.
Если агент вместо исполнения отправляет ключ на веб-сервер, требование
«веб-сервер вообще не получает ключ» уже не выполняется.

Выход из браузера не мешает агенту. Но выключение компьютера, сон, отсутствие
интернета или остановка программы мешают. После восстановления не нужно
накапливать несколько коррекций по устаревшим данным: сначала свежая проверка.

DPAPI защищает данные в покое, но не делает их недоступными вредоносной программе,
работающей с достаточными правами на том же компьютере. Автозапуск и доступ к
хранилищу при выходе из Windows нужно спроектировать для выбранной учётной записи.

## 5. Независимый ключевой сеанс в RAM

Самый простой промежуточный вариант: пользователь отдельно разрешает фоновому
исполнителю держать ключ в RAM дольше браузерного сеанса. Выход из интерфейса
тогда не уничтожает этот отдельный ключевой сеанс.

Ключ не записывается в прикладные файлы/БД, но находится в процессе до отзыва
разрешения, ограничения срока или перезапуска. После перезапуска нужен ввод заново.
Защита от swap, core dump и снимков памяти — отдельная задача инфраструктуры;
строки Python нельзя считать гарантированно физически обнулёнными.

Это меняет нынешнее правило «выход удаляет ключ», поэтому нельзя включать такой
режим молча. В интерфейсе нужны отдельное разрешение, срок действия, список активных
кабинетов и кнопка отзыва. На первом этапе такое хранение не включается.

## Что не решает задачу

* Шифрованный файл и ключ расшифровки рядом: компрометация сервера даёт оба.
* Бессрочный общий токен Vault/облака в `.env`: заменяет один сильный секрет другим.
* localStorage/cookies браузера: не дают автономного исполнителя и повышают риск утечки.
* Хеш API-ключа: его нельзя использовать вместо исходного ключа для Seller API.
* Одноразовая передача ключа из браузера без фонового доверенного процесса:
  после остановки процесса получать ключ будет неоткуда.
* Фильтрация только по внешнему IP: сама по себе не подтверждает, какой процесс
  обращается к хранилищу; за одним NAT находятся разные VM и программы.

## Рекомендация для Great Equalizer

Если условие — **не сохранять ключ на диске веб-VM**, первый практичный вариант:
внешний менеджер секретов и отдельная фоновая машинная роль; ключ используется
в RAM при выполнении. Это проще, но требует честно принять риск доступа backend к секрету.

Если условие — **веб-VM вообще не получает ключ**, предпочтительнее внешний
исполнитель с собственными проверками и менеджером секретов. Для полного выноса
из физического сервера он размещается вне этого хоста. Для небольшого числа
кабинетов это больше инфраструктуры, но яснее разделяет права и ответственность.

Агент на постоянно работающем вашем устройстве — альтернатива внешнему хостингу,
если приемлема зависимость от электропитания и интернета этого устройства.

До выбора реализации нужно определить границу «не на сервере», допустимость
платного сервиса, наличие постоянно работающего устройства, способ начального
ввода ключей, права Ozon, ротацию/отзыв и правила поведения при недоступности хранилища.
Ни один из вариантов автоматически не отменяет необходимость защиты самого сайта.

Справочные продукты: [AWS Secrets Manager](https://docs.aws.amazon.com/secretsmanager/latest/userguide/intro.html),
[Google Secret Manager](https://cloud.google.com/secret-manager/docs/overview),
[Azure Key Vault](https://learn.microsoft.com/azure/key-vault/general/overview),
[Vault](https://developer.hashicorp.com/vault/docs).
